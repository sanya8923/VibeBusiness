description: Используй, когда просят «возьми задачу #N», «сделай задачу #N», «продолжи задачу #N», «выполни issue N» в проекте с процессом github-tasks. Ведёт одну задачу от захвата до PR со статусом «на приёмке»: захват без гонки с другими сессиями, своя рабочая копия, работа строго в границах задачи, проверки, коммит своих файлов, PR. Задачу не принимает и не сливает — это скилл review. НЕ выбирай задачу сам, если номер не назван, и НЕ ставь задачи этим скиллом (это task-new).

# Выполнение задачи

Процесс — `${CLAUDE_PLUGIN_ROOT}/PROCESS.md`. Скрипты — `${CLAUDE_PLUGIN_ROOT}/scripts/`,
дальше `S=${CLAUDE_PLUGIN_ROOT}/scripts`.

Аргумент — номер задачи. Нет номера — спроси, сам не выбирай.

## 1. Прочитать и взять

1. `gh issue view N --comments`. Задача — самодостаточный источник цели, плана и
   проверок; повторную разведку не проводи.
2. **Продолжение или новая работа?** Если у задачи уже стоит `in-progress` и в ней
   единственная заявка от этой сессии (`CLAUDE_CODE_SESSION_ID`) или человек прямо сказал
   «продолжи» — это продолжение: пропусти захват. Иначе — захват:
   `bash $S/claim.sh N`. Код 3 — «занято»: скажи, кто держит задачу, и остановись.
3. **Постановка полная?** Цель, «Что сделать», «Когда считаем готовым», «Не входит», без
   открытых «Не решено». Неполная — освободи задачу (`bash $S/status.sh N
   owner_decision`), напиши в неё комментарием конкретный пробел и остановись: достраивать
   решение внутри исполнения нельзя.
4. **Зависимости** («Зависит от: #M») закрыты? Нет — `bash $S/status.sh N blocked`,
   комментарий с причиной, стоп.
5. **Коротко перескажи человеку план из задачи** — цель, границы, проверки — и спроси
   подтверждения, что делать именно так. Если человек меняет решение — это работа
   скилла `task-new` (уточнение задачи), а не правка на ходу.

## 2. Работать

1. Рабочая копия: `bash $S/worktree.sh N` — последней строкой он печатает её путь. Все
   правки и команды — только в ней. Основную копию не трогай: в ней могут работать другие
   сессии. В командах git пиши путь рабочей копии **буквально** (`git -C /полный/путь …`),
   а не через переменную: хук запретов проверяет каталог по тексту команды и путь из
   переменной не раскрывает — коммит через `cd "$WT"` он примет за коммит в основную копию.
2. Делай только то, что в задаче. Нашёл проблему рядом — поставь её отдельной задачей
   (скилл `task-new`) и продолжай свою.
3. Проверь каждый пункт «Когда считаем готовым» отдельно: команда и её результат.
   Команды проверок проекта — поле `checks` в `.claude/github-tasks.json`. Чего не смог
   проверить — так и запиши «не проверено» с причиной, не подменяй ручную проверку
   догадкой.
4. Коммить поимённо только файлы задачи: `git -C /путь/рабочей/копии add путь ...`. `git add -A`,
   `git commit -a` и коммит в основную ветку хуки плагина блокируют. Перед коммитом —
   `git -C /путь/рабочей/копии status --short`: посторонние файлы в коммит не берёшь, даже если они
   лежат в рабочей копии.
5. Сообщение коммита — что и зачем; в теле — чем проверено.

## 3. Отдать на приёмку

1. Отчёт исполнителя во временный файл: что сделано; по каждому пункту «Когда считаем
   готовым» — чем проверено (команда → результат) или «не проверено» с причиной;
   отклонения от задачи и почему; ограничения.
2. `bash $S/open-pr.sh N <файл отчёта>` — push, PR с `Closes #N`, статус `in-review`.
   После возврата с приёмки тот же скрипт не создаёт второй PR: отправит коммиты и
   добавит отчёт комментарием.
3. Сообщи человеку: ссылка на PR, что проверено, что нет, и что дальше — приёмка
   скиллом `review` в другой сессии или полный цикл скиллом `cycle`.

## Возврат с приёмки

Получил вердикт «Возврат» — `bash $S/status.sh N in_progress`, исправь только
перечисленное в вердикте, проверь заново, коммит, снова `open-pr.sh`. Замечание, которое
меняет саму задачу, — не исправляй молча: остановись и уточни задачу через `task-new`.

## Чего не делать

- Не принимать свою работу и не сливать PR.
- Не закрывать задачу руками.
- Не брать вторую задачу в этой же сессии, пока первая не отдана на приёмку или не
  освобождена.

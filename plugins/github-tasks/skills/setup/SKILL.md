# Настройка проекта под процесс задач

Процесс описан в `${CLAUDE_PLUGIN_ROOT}/PROCESS.md` — прочитай раздел «Файл настроек»,
прежде чем начать. Пока в репозитории нет `.claude/github-tasks.json`, плагин в нём
выключен: хуки молчат, скрипты отказываются работать.

## Шаги

1. **Проверь окружение.** `gh auth status` — вход выполнен; `gh repo view --json
   nameWithOwner,defaultBranchRef` — репозиторий на GitHub есть. Нет — скажи, что сделать
   человеку, и остановись.
2. **Посмотри, что уже есть.**
   - `gh label list --limit 500` — метки проекта. Если среди них есть метки со смыслом
     статуса (например, `wip`, `review`, `needs-decision`), предложи сопоставить их ключам
     `ready`, `in_progress`, `in_review`, `blocked`, `owner_decision` вместо новых меток:
     так открытые задачи не потеряют статус.
   - Как в проекте проверяют код: скрипты `test`/`lint`/`build` в `package.json`,
     `Makefile`, `pyproject.toml`, файлы CI в `.github/workflows/`. Из них — кандидаты в
     поле `checks`.
   - Основная ветка; идут ли PR в неё или в другую ветку (тогда — `base_branch`).
3. **Покажи человеку одним сообщением** проект файла настроек: сопоставление меток,
   `checks`, `base_branch`, нужен ли `paths` (монорепозиторий), нужны ли хуки плагина
   (`"hooks": false`, если в проекте уже свои защиты git). Дождись согласия.
4. **Запиши `.claude/github-tasks.json`** — только согласованные поля. Образец —
   `${CLAUDE_PLUGIN_ROOT}/templates/github-tasks.json`.
5. **Запусти механику:** `bash "${CLAUDE_PLUGIN_ROOT}/scripts/setup.sh"`. Скрипт заводит
   недостающие метки, кладёт шаблон задачи, прячет `.claude/worktrees/` от git и ставит в
   README блок ссылок-фильтров. Последней строкой он печатает изменённые файлы.
6. **Отдай настройку через PR, а не коммитом в основную ветку** — с этого момента хук
   плагина запрещает коммиты в неё:
   - `git switch -c setup-github-tasks`;
   - `git add` — поимённо: `.claude/github-tasks.json` и файлы из вывода `setup.sh`;
   - коммит, `git push -u origin setup-github-tasks`, `gh pr create`.
   PR сливает человек — это включение процесса, приёмщик здесь не нужен.
7. **Отчитайся:** что заведено, какие метки сопоставлены, ссылка на PR, и что дальше —
   ставить задачи скиллом `task-new`.

## Чего не делать

- Не переименовывать, не перекрашивать и не удалять существующие метки.
- Не трогать открытые задачи проекта.
- Не выдумывать команды проверок: только то, что реально есть в проекте и что человек
  подтвердил.

# Процесс задач github-tasks

Один документ, на котором стоят все скрипты, скиллы и хуки плагина. Если поведение
скилла расходится с этим файлом — прав этот файл, а скилл надо поправить.

## Коротко

Задача — это GitHub Issue. На каждую задачу — своя ветка `issue-N` и свой PR с
`Closes #N`. Статус задачи — **только метка**, второго места статуса (доски, файла,
таблицы) нет. Работу принимает не тот, кто её делал. Задача закрывается слиянием PR,
руками не закрывается.

## Метки статуса

| Метка (по умолчанию) | Ключ в настройках | Что значит |
|---|---|---|
| `ready` | `ready` | Постановка полная, задачу можно брать |
| `in-progress` | `in_progress` | Задачу взял агент или человек, у неё есть исполнитель |
| `in-review` | `in_review` | Открыт PR, идёт приёмка |
| `blocked` | `blocked` | Ждёт другой задачи или внешнего события; причина — в комментарии |
| `owner-decision` | `owner_decision` | Ждёт решения владельца; вопрос — в комментарии |

- У открытой задачи **не больше одной** метки статуса. Скрипт `status.sh` снимает все
  остальные, когда ставит новую.
- Задача **без метки статуса** — черновик постановки: брать её нельзя.
- Имена меток настраиваются в `.claude/github-tasks.json` (раздел «Файл настроек»):
  так плагин подстраивается под метки, которые в проекте уже есть.
- Приоритет — метки `P0`…`P3` (P0 — горит). Этапы и релизы — вехи (milestone).

## Жизненный цикл

```
черновик ──постановка──▶ ready ──захват──▶ in-progress ──PR──▶ in-review
                                              ▲                    │
                                              └──── возврат ───────┤
                                                                   └── принято → слияние PR → задача закрыта
в любой момент:  blocked  (ждёт события)   owner-decision  (ждёт владельца)
```

1. **Постановка.** Задача пишется по шаблону `templates/task.md`. Перед созданием —
   поиск дублей и одобрение плана человеком. Полная постановка получает `ready`.
2. **Захват** — см. следующий раздел. После захвата: исполнитель назначен, метка `in-progress`.
3. **Работа.** Ветка `issue-N` от свежей базовой ветки, рабочая копия
   `.claude/worktrees/issue-N/` внутри репозитория. Работа строго в границах задачи;
   найденное по пути — новой задачей, не «заодно».
4. **PR.** В описании — `Closes #N`, что сделано, чем проверено (команда и результат),
   что не проверено. Метка задачи — `in-review`.
5. **Приёмка** — см. раздел «Приёмка».
6. **Слияние.** Принятый PR сливается скриптом `scripts/merge.sh <номер PR>`: он сливает
   только PR, у которого последний вердикт в комментариях — `Вердикт: Принято`. Если PR
   шёл в основную ветку репозитория, задачу закрывает GitHub по `Closes #N`. Если в другую
   (`base_branch` из настроек) — GitHub задачу не закрывает, и её закрывает тот же скрипт
   комментарием со ссылкой на PR.

**Выход из `blocked` и `owner-decision`.** Когда помеха снята, задача уходит в
`in-progress`, если у неё есть исполнитель и работа уже начата, и в `ready` — если
работа не начиналась. Переставляет тот, кто снял помеху (человек или сессия, которая
это увидела), скриптом `status.sh`.

## Захват задачи

Несколько сессий Claude часто работают под одним аккаунтом GitHub, поэтому
«исполнитель» не отличает одну сессию от другой. Захват устроен так, чтобы из двух
одновременных попыток побеждала ровно одна:

1. **Проверка.** Задача открыта, на ней метка `ready`, исполнителя нет. Иначе — «занято»,
   и сессия берёт другую задачу.
2. **Заявка.** Сессия пишет в задачу комментарий-заявку:
   `<!-- github-tasks:claim session=<id> -->` и строку «Беру в работу». `<id>` —
   идентификатор сессии Claude Code (`CLAUDE_CODE_SESSION_ID`), без него — случайный.
3. **Сверка.** Через пару секунд сессия перечитывает заявки. В сверке участвуют только
   заявки моложе 10 минут. Побеждает заявка с наименьшим номером комментария (GitHub
   выдаёт номера по возрастанию).
4. **Победитель** ставит себя исполнителем и метку `in-progress` и удаляет все остальные
   заявки в задаче, включая брошенные заявки старше 10 минут.
   **Проигравший** удаляет свою заявку и берёт другую задачу.

Заявка старше 10 минут в сверке не участвует: если сессия упала между заявкой и меткой,
её заявка через 10 минут перестаёт мешать.

**Чья задача.** После захвата в задаче остаётся ровно одна заявка — победителя: заявки
проигравших удалены ими самими, брошенные — победителем, а при каждом возврате задачи в
`ready` удаляются все заявки (см.
«Освобождение задачи»). Поэтому владелец задачи — сессия из единственной заявки в ней.

## Освобождение задачи

Задачу, взятую в работу, освобождают командой `status.sh N ready`. Скрипт ставит `ready`,
снимает исполнителя и удаляет все комментарии-заявки — следующий захват начинается с
чистого листа.

- **Сессия сама отказывается от задачи** (не может доделать, задача оказалась не той) —
  освобождает её и пишет в задачу комментарий, что сделано и почему брошено.
- **Сессия упала после захвата.** Отличить живую сессию от упавшей по GitHub нельзя: все
  работают под одним аккаунтом. Поэтому решает человек: сводка показывает задачи в
  `in-progress`, в ветке которых давно нет новых коммитов, и человек освобождает такую
  задачу. Автоматически задачи не освобождаются — иначе живая, но долгая работа
  получила бы второго исполнителя.
- **Ветка и PR после освобождения остаются.** Следующий исполнитель продолжает с них:
  `worktree.sh` подхватывает существующую ветку `issue-N`, `open-pr.sh` — открытый PR.
  Начать заново — значит явно удалить ветку и закрыть PR с комментарием о причине.

## Ветки и рабочие копии

- Ветка — `issue-N`, от свежей базовой ветки (`base_branch` из настроек, по умолчанию —
  основная ветка репозитория).
- Рабочая копия — `.claude/worktrees/issue-N/` внутри репозитория; папка
  `.claude/worktrees/` добавляется в `.gitignore`. Своя копия у каждой сессии — две
  сессии не правят одни и те же файлы на диске.
- В коммит — только файлы задачи, поимённо. `git add -A`, force push и коммит прямо в
  основную ветку запрещены хуками плагина.

## Приёмка

- **Принимает не автор.** Чат, который писал реализацию, свою работу не принимает.
  Приёмку делает агент-приёмщик плагина (только чтение и запуск проверок) или человек.
- **Доказательство — собственный запуск.** Приёмщик сам запускает проверки из
  настроек проекта и смотрит дифф. Отчёт исполнителя — подсказка, не доказательство.
  Зелёный CI на PR обязателен, если в проекте есть CI.
- **По каждому критерию** — один из статусов: «выполнен», «не выполнен», «не проверен».
- **Вердикт** — комментарием в PR, первая строка:
  - `Вердикт: Принято` — PR можно сливать;
  - `Вердикт: Возврат` — дальше список «что не так → что сделать». Приёмщик код и метки
    не трогает; исполнитель, получив возврат, сам переводит задачу в `in-progress`
    (`status.sh N in_progress`), исправляет и снова отдаёт через `open-pr.sh`.
- В полном цикле одной задачи приёмщик один: возвраты уходят ему же, чтобы сохранялась
  история замечаний.

## Как владелец смотрит задачи

Доски нет. Вместо неё — сохранённые ссылки-фильтры, скилл настройки проекта кладёт их
в README:

- на приёмке: `is:open label:in-review`
- ждёт моего решения: `is:open label:owner-decision`
- блокеры: `is:open label:blocked`
- в работе: `is:open label:in-progress`
- готово к работе: `is:open label:ready`
- черновики и задачи без статуса: `is:open -label:ready -label:in-progress -label:in-review -label:blocked -label:owner-decision`
  — сюда же попадёт задача, у которой метка статуса слетела по ошибке.

Ссылка — `https://github.com/<владелец>/<репозиторий>/issues?q=` плюс фильтр.

## Файл настроек

`.claude/github-tasks.json` в корне проекта. Пока его нет, плагин в проекте выключен:
хуки молчат, скрипты отказываются работать. Все поля необязательные. Образец —
`templates/github-tasks.json`.

| Поле | Что задаёт | По умолчанию |
|---|---|---|
| `labels` | Имена меток статуса по ключам из таблицы выше | `ready`, `in-progress`, `in-review`, `blocked`, `owner-decision` |
| `base_branch` | Куда идут PR задач | основная ветка репозитория |
| `paths` | Папки, на которые действует процесс (для монорепозитория) | весь репозиторий |
| `checks` | Команды проверок, которые запускают исполнитель и приёмщик | нет |
| `release_checks` | Проверки проекта перед релизом: `[{"name": "...", "run": "..."}]` | нет |
| `task_rules` | Дополнительные правила постановки задач, текстом | нет |
| `hooks` | `false` — выключить хуки плагина (если в проекте свои) | `true` |
